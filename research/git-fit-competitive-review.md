## 1. 结论摘要

Git-Fit 与 fitness-buddy 在**问题定义上高度重叠**（把 AI 生成等待时间转成微运动），但在**触发机制、权限成本、交互形态和系统兼容性上是四个可核验的实质差异**，因此 Git-Fit **不是 fitness-buddy 的直接替代品**，重叠程度估计为「同一问题、不同解法」。

三项最重要的可核验发现：

1. **Git-Fit 需要辅助功能权限，fitness-buddy 零系统权限。** 这是两者最硬的差异，且有双向一手证据（Git-Fit README 明写要求；fitness-buddy 代码显式关闭该权限）。
2. **Git-Fit 代码自 2026-01-23 起未再推送**，截至 2026-07-19 约 6 个月无提交活动（GitHub API `pushed_at`）。它不是一个正在快速迭代、会碾压后来者的对手。
3. **Git-Fit 有一个仍开放的「在真正写代码时误触发」issue（#4）**，而这正是 fitness-buddy「打字即收起」所针对的问题。这是目前唯一一条**来自竞品真实用户、指向 fitness-buddy 差异点**的外部证据——但只有 1 名用户，证据强度弱。

建议（详见第 11 节）：**继续差异化验证，不调整定位，不暂停**；但必须把验证重点从「桌宠是否可爱」移到「零权限 + 不误触发」这两条有外部证据支撑的差异上。

## 4. 触发机制与技术实现对照

这是两者**最实质的技术差异**。

### Git-Fit（可核验事实）

- 检测对象是**高 CPU 开发进程**：README 点名 `xcodebuild`、`cursor`、`docker`。
- 触发条件：进程活跃 **且用户离开 IDE 窗口**时触发。
- v1.3.0（2026-01-23）发布说明原文要点："GitFit now only triggers when Claude is _actually working_ (CPU > 5% sustained for 2 seconds)"，目的是消除**空闲 Claude 会话的误触发**。
- 架构：v1.3.0 提到 XPC Service 以维持沙箱。
- 语言 Swift（占 93.1%），原生 macOS。

### fitness-buddy（本仓库代码核验）

- 检测对象是**系统空闲时间 + 前台 App 名称**：`app/activity-detector.js:28` 使用 Electron `powerMonitor.getSystemIdleTime()`；前台 App 经 `get-windows` 的 `activeWindow`。
- 触发条件（README 第 40 行 + NOW.md 第 21 行）：休息**到期** → 再等**停手 ≥30 秒**的自然停顿才弹；**打字时绝不弹**；全屏（编码工具除外）或会议软件前台不弹；离开 ≥5 分钟算自然休息。

### 差异的实际含义

| | Git-Fit | fitness-buddy |
|---|---|---|
| 触发信号 | 机器在忙（CPU/进程） | 人停手了（输入空闲） |
| 语义 | "AI 正在跑，你有空档" | "你已经停手 30 秒，且到该休息的时候了" |
| 误触发风险 | 机器忙但人在写代码 → 打断 | 人停手但只是在读文档/思考 → 可能不合时宜 |

**关键外部证据**：Git-Fit issue **#4「Disable when actually coding」（2026-01-21 创建，截至 2026-07-19 仍 open）**——用户报告在 VS Code 中**手动写代码时**被触发。这在结构上正是「以机器忙为信号」的固有代价，而 fitness-buddy 的「打字即收起」直接针对它。

**证据强度标注**：该 issue 是**真实第三方用户**反馈（强于自我判断），但**仅 1 例且未关闭**，不能推断为普遍痛点。

## 5. 权限、隐私与安全对照

| 维度 | Git-Fit | fitness-buddy |
|---|---|---|
| 辅助功能权限 | **必需**。README 原文："Required to detect when your IDE is the active window" | **不需要**。`app/activity-detector.js:56` 显式传入 `{ accessibilityPermission: false, screenRecordingPermission: false }` |
| 录屏权限 | 未见要求 | 显式关闭 |
| 数据上传 | 无后端；README："No analytics. No telemetry" | 本地 JSON 存储（`app/store.js`），无后端 |
| 读取代码/按键 | README 明确否认 | 只取前台 App 名称，不读窗口标题、不录屏（README 第 98–101 行） |

**结论（可核验事实）**：两者**隐私姿态都是本地优先、都不上传**，在这一点上**不存在差异**——不应把"本地优先"当作 fitness-buddy 的卖点。

**真实差异只在安装门槛**：Git-Fit 要用户过一次 macOS 辅助功能授权弹窗，fitness-buddy 不用。fitness-buddy README 第 99–101 行还记录了一个具体工程细节：若不显式关闭，`get-windows` 的辅助程序会**每次调用都弹一次授权框**。这说明零权限是一个被主动解决的设计选择，而非偶然。

**反向诚实说明**：零权限是有代价的。仅凭前台 App 名称 + 系统空闲时间，fitness-buddy **无法知道 AI 是否真的在跑**；Git-Fit 的 CPU 检测在"确认 AI 确实在工作"这件事上更准。这是一个**真实的能力劣势**，不应回避。

## 8. fitness-buddy 可能的差异及其证据强度

按证据强度排序，**从强到弱**：

### A. 零系统权限 —— 证据强：**强（事实层面）**
双向一手证据：Git-Fit README 明写必需辅助功能权限；fitness-buddy 代码显式关闭。
**但是**：「安装时少一个授权弹窗」是否会改变任何人的采用决定，**完全未验证**。这是事实差异，不是已证实的用户价值。

### B. 不在真正工作时打断 —— 证据强：**中（有外部用户信号）**
Git-Fit issue #4 是一名真实第三方用户报告的痛点，且仍未关闭。fitness-buddy 的「打字即收起 + 停手 30 秒」直接针对该问题。
**但是**：n=1，且 fitness-buddy 自己的策略也可能在"读文档/开会思考"时误触发——只是误触发的模式不同，不必然更少。

### C. 系统兼容性 —— 证据强：**中**
Git-Fit issue #1 显示 Sequoia 用户被完全挡在门外。fitness-buddy 基于 Electron，无此限制。这是一条**被竞品用户实际抱怨过**的准入门槛。

### D. 覆盖面更宽（喝水/护眼/非开发者） —— 证据强：**中（事实清楚，价值未知）**
功能事实明确。但"更多提醒类型"也可能等于"更烦"，方向未定。

### E. 桌宠形态 —— 证据强：**弱（目前是开发者自我感觉）**
这是 fitness-buddy 最投入的差异，却是**证据最少的一条**。目前没有任何外部数据支持"桌宠比菜单栏更难被忽略"，验证计划第 1 问和判断标准中"用户觉得桌宠遮挡或幼稚"恰恰把它列为可能的失败原因。**必须诚实标注：这条目前属于假设，不是优势。**

### F. 动作库更丰富（23 个 + 原理说明） —— 证据强：**弱**
fitness-buddy 侧可核验（seed.json 实测 23 条）；Git-Fit 侧**未知**（未公开清单），因此**这是一个无法成立的对比**，不应对外宣称"我们动作更多"。

## 9. 最大未知与风险

**关于 Git-Fit（未知，不猜测）**
1. 真实用户量与留存：官网「12,847 developers」未能复核，且与公开活跃度量级不符。
2. 6 个月无推送的原因：放弃 / 转私有 / 已稳定，无法区分。
3. 完整功能集：闭源 + 官网不可达，功能盘点必然有缺口。
4. 是否已有付费或商业化。

**关于 fitness-buddy（本方风险）**
5. **核心风险未变**：3–5 人 × 3 天验证尚未开始，完成率、跳过率、打扰感全部为零数据。竞品分析**不能替代**这项验证。
6. 桌宠形态可能是负资产（遮挡、幼稚），且它恰是投入最大的部分。
7. 零权限的代价：无法确认 AI 是否真在运行，触发时机可能不如 CPU 检测精准。
8. 未签名 DMG 需要用户手动 `xattr` 或右键打开——**fitness-buddy 自己也有安装摩擦**，不比 Git-Fit 的权限弹窗轻。这一条容易被自己忽略。

**关于本次审查方法的局限**
9. 官网未能访问，Git-Fit 侧证据**偏向 GitHub 一侧**，可能低估其产品完成度与市场表现。结论应据此打折。

## 10. 下一项最小验证实验（无需继续开发）

**实验：安装摩擦与首次印象测试（不需要连续 3 天，不需要写任何代码）**

- **对象**：3 名长时间电脑工作者（HANDOFF 记录西西当前缺少符合条件的熟人候选者，因此此实验特意设计为**门槛极低、可公开招募**）。
- **动作**：只让对方完成「下载 → 打开 → 走完首次问卷 → 看到灵狐出现」，**共约 5 分钟**，然后立刻回答 4 个问题。
- **记录**：
  1. 是否卡在未签名警告？卡住的用什么方式解决/放弃？
  2. 看到桌面上出现灵狐的**第一反应**是什么（原话记录）？
  3. 「它不需要任何系统权限」——这句话对你有区别吗？
  4. 你愿意让它在桌面上开一整天吗？为什么？

- **为什么是这个实验**：它用最小成本同时打到**证据最弱的两条差异**——问题 2 直接测 E（桌宠形态，目前纯假设），问题 3 直接测 A（零权限，事实清楚但价值未知）；问题 1 顺带暴露 fitness-buddy 自己的安装摩擦（风险 8）。
- **明确不做**：不安装 Git-Fit 做对照（违反本任务安全约束，且需要 Tahoe + 辅助功能权限）。
- **与既有计划的关系**：这是 `docs/04-validation-plan.md` 3 天验证的**前置漏斗**，**不替代、不修改**该计划的任何指标与判断标准。若连 5 分钟首次印象都留不住人，3 天验证无从谈起。

## 11. 建议

### 建议：**继续差异化验证**（不调整定位，不暂停）

**理由（均基于本次核验的证据）**

1. Git-Fit 不构成直接替代：触发信号（机器忙 vs 人停手）、权限成本、系统兼容性三项均为实质差异，且后两项有竞品用户实证抱怨（issue #1、#4）。
2. Git-Fit 未占据这个位置：39 stars、1 watcher、6 个月无推送、闭源无 license——公开证据不支持"赛道已被赢下"。
3. 但也**不能反向乐观**：Git-Fit 的存在同样**没有证明**需求成立。fitness-buddy 的核心风险仍是自己的零外部数据。

**建议附带的定位微调（不改主线、不改验证标准）**

对外表述的重心应从「可爱的桌宠」转向**有事实支撑的两条**：不用给任何系统权限；你在打字时它绝不弹。前者是硬事实，后者有竞品用户实证背书。桌宠仍是形态，但在拿到数据前**不应作为主要卖点宣称**。

### 推翻本建议需要什么新证据

- **转向「暂停」**，若出现任一：第 10 节实验中 3 人里 ≥2 人对桌宠的第一反应是负面（遮挡/幼稚/想关掉）；或 3 天验证完成率 <50%、打扰感 >3 分（`docs/04-validation-plan.md` 既有标准）。
- **转向「调整定位」**，若出现：用户明确表示零权限对他们无所谓，且真正想要的是"确认 AI 真的在跑"的精准触发——那意味着 Git-Fit 的技术路线更对，fitness-buddy 需重新考虑触发信号。
- **需要重估整个竞争格局**，若出现：Git-Fit 官网可访问并能独立佐证其用户量级；或 Git-Fit 恢复更新并补上「打字不打断」。

**本报告不改变项目主线状态。** fitness-buddy 是否成为主线，仍待西西确认，且应以真实用户验证数据为准，而非竞品分析结论。
